# tetris-arena

Standalone spinoff of the Tetris game embedded in [saiushi](../saiushi) (the owner's personal site). Purpose: experiment with real-time 1v1 online Tetris without touching the main site. Scoped explicitly as a **personal test sandbox** — no accounts, no payments, minimal ops, optimize for fast iteration over production rigor. See [README.md](README.md) for setup steps (npm install, Supabase project + SQL, env vars).

## Status

- **Phase 1 (done):** ported the single-player game (Zen/Sandbox, 40 Lines, Blitz) out of saiushi as a standalone Next.js app. `TetrisGame.tsx`, `TitleScreen.tsx`, `TetrisApp.tsx`, `tetrisConstants.ts` are otherwise-unmodified copies of the saiushi originals — keep gameplay fixes portable between the two where reasonable. Dropped: Sanity CMS (background themes are a one-theme local stub in `UseBackgroundTheme.ts`), the modal wrapper, `framer-motion`, and everything non-Tetris (blog, fortune slip, audio player).
- **Phase 2 (done):** room/lobby + synchronized start over Supabase Realtime, plus a `'versus'` mode on `TetrisGame` (races to 40 lines like Sprint). Verified end-to-end against a live Supabase project (two-tab test: presence sync, ready-up, synchronized start).
- **Phase 3 (done):** garbage-line exchange. Clearing lines sends an attack (standard-ish table: Single/Double/Triple/Tetris → 0/1/2/4, T-Spin Single/Double/Triple → 2/4/6, +1 for back-to-back, plus a combo bonus table) to an opponent over the same room channel; your own attack cancels incoming garbage before it lands (netted at your next piece lock, not instantly). `useOnlineRoom()` was lifted from `OnlineLobby` up into `VersusApp` so the Realtime channel survives the lobby→match handoff instead of being torn down when `OnlineLobby` unmounts.
- **Phase 4 (done):** rematch (a "Rematch" button on the post-match screen resets the ready/start state and returns to the *same* still-connected room's lobby instead of tearing it down, so everyone just ready up again — see `resetMatchReady` in `useOnlineRoom.ts`); a shared seeded 7-bag RNG (mulberry32, seeded once per match by the host alongside `startAt`) so every player sees the identical piece sequence, live-verified by reading matching NEXT-queue colors out of two tabs' DOM; and Quick Play — a public matchmaking queue (`useQuickplay.ts`, channel `tetris-quickplay-lobby`) that auto-groups strangers without a shared code, using presence + a deterministic sort-and-group algorithm (no server, so no locking — see the accepted-race-condition note below) rather than negotiation.
- **N-player rooms + match rules (done):** `useOnlineRoom`'s presence/ready-up/broadcasts are generalized from "exactly one opponent" to a list (`opponents`, `readyGuestIds`, `MAX_ROOM_SIZE = 8`), and Quick Play groups up to 8 simultaneous searchers instead of just pairing two. The actual match logic is N-ready too, not just the lobby scaffolding: garbage attacks target a **random still-alive opponent** (`VersusApp`'s `handleAttack`, using `sendGarbage`'s `targetGuestId`), the win condition is **pure last-player-standing** (clearing lines no longer wins on its own — a match ends only when you top out, or every other opponent is gone), and opponent board previews (`MiniBoard`, one per opponent, broadcast once per piece lock) render however many opponents are in the room. `VersusApp` snapshots the room's roster (`matchOpponents`) the instant a match starts rather than reading live presence throughout, so someone's tab closing mid-match can't shift the win-condition denominator — it can still shift who counts as *eliminated*, though, see below.
- **Disconnects count as eliminations (done):** `useOnlineRoom`'s presence-sync handler diffs each update against the previous snapshot (`opponentsRef`) — anyone who silently drops off presence (tab closed, connection lost) without ever broadcasting `'eliminated'` gets added to `eliminatedGuestIds` anyway, the same set an explicit elimination populates. Closes what was previously an accepted gap: survivors' last-player-standing win condition no longer stalls forever against a player who just leaves.
- **Routing:** single player is `/`, Versus is its own `/versus` route (chosen explicitly over keeping it as view-state, so rooms are shareable as `/versus?code=XXXXX` links — the host's lobby screen has a "Copy Join Link" button for this). A persistent top nav (`NavBar.tsx`) has a "Play ▾" dropdown split into **Local** (`/?mode=standard|sprint|blitz`, deep-links straight into that mode) and **Online** (`/versus`) — modeled loosely on Jstris's nav, deliberately without the rest of Jstris's chrome (no Leaderboard/Maps/About pages, no login, no chat, no live-board grid) since that's out of scope for now.
- **Match stats, session-scoped (done):** live "Sent"/"Received" garbage-line counters in the versus HUD (`linesSent`/`linesReceived` state in `TetrisGame.tsx`, accumulated at the same `lockPiece` call sites as the garbage logic itself), and a "Wins this session" counter (`winCount` in `VersusApp.tsx` — survives rematches, resets on a full Quit) shown in `OnlineLobby`'s ready-up screen rather than on `TetrisGame`'s win/lose result screen, so it's visible right where you'd decide whether to keep playing. - **PPS/APM/attack-per-minute, live (done):** Pieces Per Second and Actions Per Minute in Sprint, Blitz, and Versus's HUD (Sandbox excluded — it's a goalless practice mode, these don't mean much there), plus Attack/Min in Versus. - **Hydration warning fixed (done):** `/` and `/versus` both prerender statically (`○ Static` in the build output), so `useSearchParams()` — wrapped in `<Suspense>` per Next.js's own required pattern — had no real request to read at build time and bailed that boundary to client-only rendering (visible in the raw SSR HTML as a `data-dgst="BAILOUT_TO_CLIENT_SIDE_RENDERING"` marker). ## Architecture notes

- **Realtime, no rooms table.** `useOnlineRoom.ts` uses a Supabase Realtime channel named `tetris-room:<code>` purely for presence (who's in the room) and broadcast (ready/start events) — no Postgres table backs a room. Keeps setup to one SQL block (just `tetris_scores` for the leaderboard).
- **Client-authoritative.** Each client runs its own board locally; only high-level events (ready, start, garbage, eliminated, board-snapshot) cross the wire. No server-side validation — acceptable for a sandbox among friends, would need revisiting before anything adversarial.
- **Synchronized start without teaching TetrisGame about Supabase.** The lobby computes a shared `startAt` timestamp + RNG seed (host decides once everyone's ready, broadcasts both) and every client's `setTimeout` to *mount* `TetrisGame` at that instant. Since `TetrisGame`'s own internal 3-2-1-GO countdown then runs identically on all sides from the same starting instant, gameplay begins in lockstep. `TetrisGame.tsx` still has zero direct knowledge of Supabase/Realtime — its multiplayer surface is a handful of plain optional props (`onAttack`, `incomingGarbage`, `onEliminated`, `eliminatedOpponentIds`, `opponentCount`, `onRematchMenu`, `seed`, `onBoardUpdate`, `opponentBoards`) that `VersusApp` wires to `useOnlineRoom()`'s send functions/broadcast state (with `VersusApp` doing the random-target selection itself, per the note above), keeping the game component transport-agnostic and free of any room-topology awareness.
- **No server, so no locking — accepted for a friends-scale sandbox.** Both the room's ready-up and quickplay's matchmaking are computed independently by each client from its own (eventually-consistent) view of Realtime presence, not negotiated with a central authority. This is occasionally observable: e.g. if 3 people click Quick Play within the same instant, presence sync can momentarily disagree and one person can be left waiting alone rather than grouped in — recoverable by just searching again (confirmed live: this happened in testing, and the leftover player matched normally on a second attempt). Not worth a locking table for this project's scale.
- **Ephemeral identity.** A random guest ID per browser tab (`useOnlineRoom.ts`/`useQuickplay.ts`), nothing persisted, no login.
- **Known accepted lint noise:** this codebase carries a fixed baseline of experimental React-Compiler ESLint findings (`react-hooks/set-state-in-effect` etc.) inherited from the saiushi original — same 9 findings there, plus a few more added deliberately since: `useOnlineRoom.ts`'s host-decides-start effect, and the mount-only "read a client-only source (localStorage/URL), then setState once to sync it in" shape shared by `useSearchParam.ts` and `useColorTheme.ts` (both intentionally hydration-safe — state starts equal to the SSR default, then a mount effect reads the real client-side value; there's no way to do that read outside an effect). Consistent with the existing baseline's shape, not something worth restructuring for a sandbox hook. Don't chase these to zero; just don't let the count creep up for reasons unrelated to that pattern.
